# Homeowner app fixes — 21 October 2026

## App changes

- Home category navigation starts in results mode. It no longer autofocuses an
  empty Browse field over an in-progress category search. ZIP coverage enriches
  the location independently of results; late counts cannot overwrite the
  selected search's authoritative count.
- Home All and Browse all categories use the same service-tile component, with
  all 31 services in four columns. Narrow layouts keep whole words together;
  full names remain available to accessibility and tooltips.
- Profile availability uses the recent search snapshot when supplied. Profile
  and any necessary fallback availability load before revealing the complete
  surface, eliminating the second layout change. Booking still validates slots
  at hold and handles calendar conflicts.
- Restored the green availability capsule alongside the price. Batch 21
  amendment 1, R4 (line 536 of the supplied document) explicitly puts it in the
  top-right of the price card. Batch 32 A13 concerns search cards; the calendar
  spec E1 prescribes a day-only capsule. No later instruction was found moving
  the profile's capsule below the price.
- Removed the Bookings heading at the user's explicit request, superseding
  Batch 31 C1 for this title.
- Chat uses explicit contractor profile IDs separately from Stream user IDs.
  Existing shared jobs still resolve through their work-order IDs. New
  enquiries use the server's canonical thread endpoint and require the backend
  patch below. Missing optional job-picker data does not block an enquiry.
- Chat input disables the inherited inner fill/borders, retaining one rounded
  SDK outline with a blue focus border.
- Concurrent identical searches share one request; HTTP sockets are reused.
  Search cards use the availability already supplied by search rather than
  launching up to 12 extra slot requests. Connected chat sessions are reused;
  push registration no longer delays opening the composer.

## Backend dependency: deploy before claiming live chat is fixed

`backend/chat-enquiries-and-provisioning.patch` targets
`tradeworksai/tradeworks-platform/backend/services/api/batch8_routes.py`, base
blob `20e903a0b46ece6161cbf7ed83f913fc98dc704f`. It has been apply-checked against
the fetched source and tested locally; it has **not been deployed**.

The current server explicitly returns `work_order_required` for profile-only
requests. It also creates channels without first provisioning both users in
Stream, so a pro who has never opened chat may not exist there yet.

The patch allows authenticated homeowners to initiate enquiries to public
contractor profiles, resolves participants on the server, provisions both users,
and retains canonical `tw-{homeowner}-{contractor}` channels. Contractors cannot
initiate new enquiries. Existing server-created enquiries remain available to
their two members through list/read/send routes. Owned-job validation, supplied
contractor matching, and optional per-message work-order ownership checks stay.

From a clean platform checkout, first verify and then apply:

```powershell
git apply --check PATH/TO/HomeOwners-App/backend/chat-enquiries-and-provisioning.patch
git apply PATH/TO/HomeOwners-App/backend/chat-enquiries-and-provisioning.patch
```

From this app checkout, test the actual patched platform file:

```powershell
$env:TRADEWORKS_CHAT_ROUTES = 'PATH/TO/tradeworks-platform/backend/services/api/batch8_routes.py'
python -m unittest backend.tests.test_chat_threads_patch -v
```

Nine tests exercise public/private profiles, participant provisioning, foreign
orders, mismatched profile IDs, canonical thread reuse, member validation and
contractor initiation restrictions. Production sign-in, delivery to a second
device, attachments and push still require a live authenticated smoke test after
deployment. The app repository cannot deploy the platform's Cloud Run service.

## Performance evidence and limits

An unauthenticated read-only probe from this machine to the configured hosted
API returned Plumbing search for ZIP 33578 in **7,120 ms** (HTTP 200, two results)
and ZIP coverage in **1,258 ms** (HTTP 200). These are single-request observations,
not a benchmark. Removing serial waits, duplicate requests and socket setup
reduces client overhead; it does not establish millisecond fresh backend loads.
Backend search latency must be profiled and addressed separately. Existing
cache reuse remains in place; the new regression verifies one request for two
concurrent callers and no extra request for the immediate subsequent caller.
